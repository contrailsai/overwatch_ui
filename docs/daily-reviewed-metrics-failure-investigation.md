# `daily_reviewed_metrics` Failure Investigation

## Context

Production logs surfaced repeated errors:

```
Failed to update daily_reviewed_metrics
app_action: updateClientReviewedMetrics
app_caller: supabase/metrics
error_message: [object Object]
```

Investigation used Grafana Loki logs and a Tempo trace. This doc captures what failed, why, and what to fix.

**Environment:** Next.js App Router, Supabase (metrics tables), MongoDB (cases/posts), OpenTelemetry → Loki/Tempo.

## What Happened

A client initiated a **bulk takedown of 18 cases**. For each case, the app calls `updateClientReviewedMetrics` in parallel from `initiateTakedown`:

- `src/app/(dashboard)/cases/takedown_actions.js`
- Same pattern exists in `updateClientStatus` (`src/app/(dashboard)/cases/actions.js`)

The takedown itself completed and returned success. Metrics updates failed silently because each call is wrapped in `.catch()` and only logs an error.

### Trace evidence

From Tempo for trace `409b987a738f58cae6cb0fabbe096e56`:

| Observation | Count |
|---|---|
| GET requests to `daily_reviewed_metrics` | 18 |
| POST/PATCH requests to `daily_reviewed_metrics` | **0** |

Platforms queried: `youtube`, `instagram`, `x` — all for `project_name=Ambani`, `date=2026-06-05`.

**Conclusion:** Failure occurs on the **initial SELECT**, before any insert or update runs.

### Volume

~**59 occurrences in the last 24 hours** at time of investigation — recurring production issue, not a one-off.

## Root Cause (High Confidence)

### 1) `.maybeSingle()` fails when duplicate rows exist

`updateClientReviewedMetrics` fetches the daily row with `.maybeSingle()`:

```js
// src/utils/supabase/metrics.js
const { data: existing, error: fetchError } = await supabase
  .from('daily_reviewed_metrics')
  .select('*')
  .eq('date', date)
  .eq('platform', platform)
  .eq('project_name', project_name)
  .maybeSingle()

if (fetchError) throw fetchError
```

`.maybeSingle()` returns an error when **more than one row** matches the filter. PostgREST typically returns:

```
code: PGRST116
message: JSON object requested, multiple (or no) rows returned
```

Because the trace shows 18 GETs and zero writes, the fetch step is throwing before insert/update logic runs.

### 2) No unique constraint on the natural key

Schema (`supabase/tables info`):

```sql
create table public.daily_reviewed_metrics (
  id bigint generated by default as identity not null,
  project_name text null,
  date date null,
  platform text null,
  reviewed json null,
  risk json null,
  total_reviewed integer null,
  ...
);
```

There is **no** `UNIQUE (date, platform, project_name)` constraint.

By contrast, `client_logs` has `unique (client_id, project_name, date)` and handles insert races — which explains why `client_details` / `client_logs` updates succeeded in the same trace while `daily_reviewed_metrics` did not.

### 3) Bulk parallel updates amplify the problem

Bulk actions run metrics per post in `Promise.all`:

```js
await Promise.all(posts.map(async post => {
  await updateClientReviewedMetrics(project, currentReviewData, previousReviewData)
}))
```

Many cases share the same platform (e.g. 10× instagram). Concurrent reads/writes against the same `(date, platform, project_name)` bucket can:

1. Race on insert when no row exists yet → duplicate rows accumulate
2. Hit existing duplicates → `.maybeSingle()` fails with PGRST116

The same fetch-then-insert/update pattern exists in `updateDailyMetrics` for `daily_case_metrics`, which has the same schema gap.

## Secondary Issue: Observability Gap

Logs show `error_message: [object Object]` instead of the real Supabase error.

In `src/utils/otel-logger.js`, `otelLogError` does:

```js
if (error instanceof Error) {
  attrs.error_message = error.message
} else if (error != null) {
  attrs.error_message = String(error)  // → "[object Object]" for PostgREST errors
}
```

Supabase/PostgREST errors are plain objects (`{ message, code, details, hint }`), not `Error` instances. The actual error code (likely `PGRST116`) is dropped in Loki, making production debugging harder.

## Verification Steps

Run in Supabase SQL editor:

```sql
-- Find duplicate metric rows
SELECT date, platform, project_name, COUNT(*) AS cnt
FROM daily_reviewed_metrics
GROUP BY date, platform, project_name
HAVING COUNT(*) > 1
ORDER BY cnt DESC;

-- Check Ambani on the incident date
SELECT *
FROM daily_reviewed_metrics
WHERE project_name = 'Ambani'
  AND date = '2026-06-05'
ORDER BY platform, id;
```

If any `(date, platform, project_name)` group has `cnt > 1`, that confirms the `.maybeSingle()` failure mode.

## Recommended Fixes

### Priority 1 — Observability

Update `otelLogError` in `src/utils/otel-logger.js` to extract `message`, `code`, and `details` from PostgREST-shaped error objects (not only `instanceof Error`).

### Priority 2 — Data cleanup

Merge or delete duplicate `daily_reviewed_metrics` rows for affected `(date, platform, project_name)` tuples before adding constraints.

### Priority 3 — Schema

Add a unique constraint to prevent future duplicates:

```sql
ALTER TABLE daily_reviewed_metrics
ADD CONSTRAINT daily_reviewed_metrics_day_platform_project_unique
UNIQUE (date, platform, project_name);
```

Consider the same for `daily_case_metrics` if it follows the identical pattern.

### Priority 4 — Application logic

For bulk actions (`initiateTakedown`, `updateClientStatus`):

- **Aggregate by platform** and call `updateClientReviewedMetrics` once per platform bucket (not once per post), or
- Switch to an **upsert** / RPC that atomically increments counters, or
- **Serialize** metrics updates per `(date, platform, project_name)` to avoid races

`updateClientReviewedMetrics` itself could also replace `.maybeSingle()` with `.limit(1)` plus explicit duplicate handling, but the unique constraint + upsert is the durable fix.

## Summary

The production error is a **silent metrics tracking failure**, not a takedown failure. Bulk takedown triggered 18 parallel `updateClientReviewedMetrics` calls; all failed on the Supabase SELECT because `.maybeSingle()` cannot handle duplicate rows for the same `(date, platform, project_name)`. Missing unique constraints and parallel per-post updates make duplicates likely. Logs show `[object Object]` because PostgREST errors are not serialized correctly in OTLP logging.
